# Prefix-cache safety status

Native prompt caching is **unsupported** in the running application. `FF_PROMPT_PREFIX_CACHE` defaults off; setting it does not select a new provider, send native Messages requests, or add cache markers. The existing encrypted-credential provider factory and ordinary orchestrator call remain authoritative. There is no registered native profile, production prefix approval, warm-up call, saved-prompt store, or cache-management service.

The policy, native payload/response codecs, and synthetic comparison in this directory are offline preparation. Their passing fixtures establish local behavior only. They do not qualify native transport, native admission, provider isolation, retention acceptance, or provider savings. Issue [331](https://github.com/AstralDeep/AstralDeep/issues/331) remains a prerequisite for [333](https://github.com/AstralDeep/AstralDeep/issues/333).

## Approval boundary

An `ApprovedPrefix` binds the SHA-256 of the exact public static instruction text and the SHA-256 of the **complete ordered tool-definition list**, serialized as canonical JSON with all fields included. Tool names, local registration, and in-process transport convey no approval. A system-only approval covers an empty tool list. Descriptions, schemas, additional fields, tool order, and instruction changes invalidate the matching approval. Malformed, oversized, recursive, imported-marker-bearing, and unestimated definitions remain ineligible.

Marker application requires the current policy, its matching revision, the approved instruction block, matching model, and matching complete final tool definitions. This final check prevents a decision from being reused after the payload changes. Markers occur only on approved tools and the first approved static system block; dynamic system suffixes and messages remain outside them. Supplied markers are stripped. Production approval records must additionally retain reviewer, review time, and public/non-PHI provenance before any registration is authorized; synthetic test records grant no production approval.

## Native prerequisite implementation

The smallest dependency change belongs at `client_factory.build_llm_client`, after the existing owner/system encrypted credential resolution. Add an explicit default-off native provider preset/profile and retain profile identity and the existing captured credential revision in the resolved configuration. The factory should return the consumer-compatible completion/stream interface, preserving `_call_llm`, its ordinary tool dispatch, `_context_model_call`, invocation accounting, durable permits, PHI/permission/LETS gates, audit, and persistent-agent output caps. Never infer native capability from endpoint or model spelling.

Use `shared.external_http` for the native request. Its synchronous bounded response helper is sufficient for a bounded non-streaming implementation, but its current API cannot return cancellable incremental SSE. A native streaming implementation needs an approved async streaming helper with bounded request/event/aggregate bytes, fixed headers, explicit TLS/redirect/timeouts, disabled environment proxy/header/credential influence, deterministic DNS/egress denials, and response closure on cancellation. The current `allowed_private_hosts or environment` fallback also needs an explicit-empty-allowlist correction before it can establish ambient-input isolation. None of these missing interfaces is supplied by the offline codecs.

The adapter must reject unsupported formats and invalid/incomplete tool arguments, preserve opaque signed/redacted continuations only when qualified, and normalize refusal/truncation/error/cancellation without inventing successful completion. Native cumulative usage must feed the existing `llm_config.invocation` and `orchestrator.context_usage` consumers; absent counters remain unknown. Inclusive input is uncached input plus cache writes plus cache reads, counted once. Reuse `context_token_accounting` for conservative request bounds. Its current qualified tokenizer profiles cover OpenAI; its fallback does not prove a native cache minimum. Cache admission therefore remains unknown until the native profile supplies a qualified bound.

Before enabling caching, bind approval and measurements to verified owner, provider, model, explicit profile, captured credential/config revision, policy revision, and tool digest. Preserve bounded uncached admission, and revalidate each request. Add retention notice/version handling and exact-candidate configured-auth synthetic staging, including failures and cancellation. No deployment, real-provider call, or user sign-in was performed for this repair.

## Provider limits and evidence

The [official prompt-caching documentation](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), inspected 2026-10-28, documents workspace cache isolation, refresh on reads, and no manual clearing. Workspace isolation does not establish Astral owner isolation. Local invalidation prevents future use; it does not delete provider data or promise immediate purge. Actual owner partitioning must be demonstrated before caching can be enabled.

The synthetic report models separate entries by owner/provider/model/profile/configuration/policy/prefix, with refresh on a simulated hit. This is a hypothetical local partition, not evidence of provider cache keys. Token prices and latency are declared model assumptions, not measured provider prices or performance. Retain exact request/response wire fixtures, all denominators and unknown outcomes, and actual authenticated staging identities when the dependency is implemented; no native savings or retention qualification is established here.
