# Ticket contract, `astral.ticket/v1`

Every effect carries a ticket with four parts. The executor, which may be the same device, another device of the owner or an institution's node, verifies all four offline. This document fixes the ticket object, the Biscuit capability chain, the action digest, the consent, the receipt binding and the labels.

Reference code: `reference/astral_mesh_ref/ticket.py` and `consent.py`. Vectors: `ticket.json`.

## 1. The ticket object

A ticket is a JSON object with exactly `v` (1), `capability`, `receipt` and `consent`.

| Part | Field | Says |
|---|---|---|
| Capability | `capability`: unpadded base64url of a Biscuit token | Who acts for whom, on which tool, with which argument digest, until when. Carries the labels |
| Receipt | `receipt`: a LETS receipt object | This effect was counted against a budget |
| Consent | `consent`: a consent object or null | The owner approved this exact action |
| Labels | Facts in the last block of `capability` | The flow labels of the decision |

Any other shape raises `ticket.malformed`.

## 2. The action and its digest

The host draws a consent prompt from the **action**, never from model output. The action is a JSON object with exactly these fields.

| Field | Value |
|---|---|
| `v` | `1` |
| `mesh` | The mesh id |
| `device` | Device id of the proposing device |
| `turn` | Event id of the `chat.turn_start` event. A member that runs a request outside the engine uses the id of the `request.send` event (`requests.md` section 5) |
| `agent` | The id of the agent that makes the call. With sub-agents, the last in the chain |
| `tool` | The tool name |
| `tool_def` | Hash of the tool's definition as pinned at approval |
| `args_digest` | Hash of the canonical JSON of the arguments |
| `influence` | Sorted event ids that influenced the turn, from the label sources |

The **action digest** is the hash of the canonical JSON of the action. Anything else raises `ticket.malformed_action`.

## 3. The capability

The capability is a Biscuit token (version 3 datalog, the `biscuit-auth` library). Its root key is the device's Ed25519 operations key. Its blocks, in order, are one per hop.

| Block | Actor fact | Facts | Checks |
|---|---|---|---|
| 0, device | `actor("device:<device id>")` | `mesh`, `device`, `feed` (the operations key as base64url), `stop_counter` | `mesh_ctx($m), mesh($m)`, the stop check, and an expiry on `time` |
| 1, turn | `actor("turn:<turn id>")` | `turn` | the tool must be in the turn's tool set, and an expiry on `time` |
| 2 to n-2, agent | `actor("agent:<agent id>")` | none | the last agent block pins `agent($a), $a == "<agent id>"` |
| n-1, call | `actor("call:<action digest>")` | `label("integrity", ...)`, `label("confidentiality", ...)`, and one `source("<event id>")` per influence | the tool equals the call's tool, `args_digest` equals the call's digest, `action_digest` equals the action digest |

Every holder may add a block and can never remove or loosen a check from an earlier block, so authority only narrows.

The exact text of the blocks is generated by `ticket.mint`. In block 0 the datalog is

```
mesh("<mesh>"); device("<device>"); feed("<feed>"); actor("device:<device>"); stop_counter(<n>);
check if mesh_ctx($m), mesh($m);
check if stop_current($n), stop_counter($c), $n <= $c;
check if time($t), $t < <expiry as RFC 3339>;
```

**Block grammar.** A verifier reads each block's source and accepts only lines that are either a `check if ...;` line or a fact of the names allowed for that block (the table above) with arguments that are plain strings of the characters `A-Z a-z 0-9 _ . : / @ = + -` (1 to 200 of them) or integers. Any rule (`<-`), unknown fact name or other argument makes the token `ticket.wrong_block_shape`. Rules would let a block derive facts that the verifier trusts. The token needs at least four blocks. The last is the call block and has exactly one actor fact with the call prefix. Block 1 is the turn. The ones between are agent blocks. Third-party blocks are refused.

## 4. Verifying a ticket

The executor knows its mesh id, the roster's feed statuses, the stop counter, the time, the action it was asked to run, the effect kind of that action, whether policy requires consent, and a callback that checks a LETS receipt. It runs these steps in order. The first failure is the error.

1. The ticket has the right shape (`ticket.malformed`). The action has the right shape (`ticket.malformed_action`). The action's mesh is this mesh (`ticket.mesh_mismatch`). The capability decodes (`ticket.malformed`).
2. The token parses as a Biscuit and its blocks follow the grammar and the layout of section 3 (`ticket.malformed`, `ticket.wrong_block_shape`). The call block carries exactly the two labels with valid values and valid source ids (`ticket.label_missing`).
3. The `mesh` fact is this mesh (`ticket.mesh_mismatch`).
4. The `feed` fact is an operations key on the roster (`ticket.bad_root`). Its device is a member (`ticket.device_removed` if removed, with the device's tickets refused outright). That device is the `device` fact (`ticket.bad_root`).
5. The `stop_counter` fact is at least the mesh's stop counter (`ticket.stopped`). A resume does not lower the stop counter, so a ticket issued before a stop stays refused after the resume.
6. The action digest equals the one pinned in the call block (`ticket.unauthorized`).
7. The token's signature chain verifies under that operations key (`ticket.bad_root`), with no third-party blocks (`ticket.wrong_block_shape`).
8. The authorizer runs with the facts `time`, `tool`, `args_digest`, `action_digest`, `agent`, `mesh_ctx` and `stop_current` taken from the request and not from the token, and a single `allow if true` policy. Any failed check is `ticket.unauthorized`. This is where an expired capability, a tool outside the turn's set, or different arguments are refused. The executor sets generous run limits. The reference retries when the library's one-millisecond default is hit and raises `ticket.limits` if it never completes.
9. The token's device, turn and last agent equal the action's (`ticket.unauthorized`). The label sources equal the action's `influence` (`ticket.unauthorized`).
10. The receipt, by the effect's kind (section 6). For a kind with a budget, the receipt is an object (`ticket.receipt_missing`). Its `type` is `lets.receipt/v1` and its `evidence_digest` is the action digest (`ticket.receipt_mismatch`). The LETS callback accepts it (`ticket.receipt_invalid`). The receipt's signature and budget are LETS's to check. For a kind without one, the receipt is null (`ticket.receipt_unexpected`) and LETS is not consulted.
11. Consent. If the consent is null and policy requires it, `ticket.consent_required`. If a consent is given, whether required or not, it must verify with kind `action` and the action digest (`ticket.consent_wrong_action` for a different action, `ticket.consent_invalid` for other failures) and its clock must be within 600000 milliseconds of the executor's time in either direction (`ticket.consent_stale`).

The result is the claims: `mesh`, `device`, `feed`, `stop_counter`, `turn`, `agents` (in order), `action`, and `labels` (`integrity`, `confidentiality` and `sources`). A verifier also reports `expires_s` (section 4.1). The executor applies its own flow rules to the labels. An institution's node never trusts a device's gates. It verifies the ticket and then runs its own.

### 4.1 Expiry and the verifier's own fold

**Expiry.** A ticket expires at the earliest of the expiry checks of its device block and its turn block. A verifier reads it from the two blocks (the check `$t < <RFC 3339>` of section 3) and reports it as `expires_s`, in whole seconds. An executor that remembers spent tickets keeps each one until `expires_s` and no longer. A token with no expiry check in either block never expires and is reported as 9223372036854775807. The ticket carries no issue time, so there is no `issued_s`. Vector kind `ticket_expiry`.

**Revoked grants and removed members.** A verifier that is itself a member of the mesh holds the roster and the grants of the mesh. It adds two refusals after step 11 and before it returns the claims. It never needs them to be current. A verifier that has not yet seen a revocation verifies offline as before.

- The device that minted the ticket is no longer a member in the verifier's roster. Step 4 already refuses this as `ticket.device_removed`, so a removed member's tickets are refused outright and no second code exists.
- A revoke in the verifier's authority fold covers the action's agent, its tool (the bare name or `<name>@<first 8 hex digits of tool_def>`) and the scope of its effect kind, and no consented grant in the same fold covers them. The error is `ticket.grant_revoked`. A key covers an action when each of its three parts is `*` or equal. A tool that was never granted and never revoked is not refused here, because the grant may live on a device the verifier has not synced with. Vector kind `ticket_grant_check` (`action`, `effect_kind`, `grants`, `revokes`).

## 5. Consent

A consent object is the one of `policy.md` section 2 with `kind` `action` and `digest` the action digest. It is signed by the presence key. The host draws the prompt from the canonical action. The digest is checked again at dispatch. A consent signed with the identity key, for another action, by a non-member, or edited, fails.

## 6. Receipt binding

The ticket carries a LETS receipt in the format LETS freezes. This contract needs two things from it. Its `type` field is `lets.receipt/v1`, and its `evidence_digest` is the action digest. LETS's device profile sets the other bindings (tenant, subject and idempotency key). When LETS publishes them they are added to this section without changing the rest.

**Which effects carry a receipt.** The budget classes of `policy.md` cover only `mesh_write` (class `notes_write`) and `outside_effect` (class `outside_effect`). Reads inside the mesh and outward reads have no budget, because the flow rules govern them, so the gate stack issues no receipt for them (`labels.md`, gate step 7). A receipt exists exactly when the kind has a budget.

- The **effect kind** is an input of the verification and never a field of the ticket. The executor derives it from its own record of the tool, the definition pinned under the action's `tool_def`, and passes one of `mesh_read`, `mesh_write`, `outward_read` or `outside_effect`. Any other value raises `labels.invalid`. A presenter cannot choose the kind, so it cannot choose to go without a receipt.
- For `mesh_write` and `outside_effect` the receipt is required and checked as in step 10.
- For `mesh_read` and `outward_read` the receipt must be null. A receipt attached to a read is refused with `ticket.receipt_unexpected`, so no receipt issued for another action can ride along and no charge is counted for a call that has none. The verifier does not call the LETS callback for a null receipt.

The ticket shape is unchanged. The field stays, and null is its value for an effect without a budget.

## 7. Verified by the kernel only

None. The Biscuit vectors are produced with `biscuit-python` 0.4.0 and the kernel's `biscuit-auth` must verify them. Each Biscuit block is signed with a fresh ephemeral key, so token bytes cannot be reproduced. The tokens are pinned in the `tokens` object of `ticket.json` and the generator reuses them. The `--check` mode checks the outcomes, not the bytes. `generate_vectors.py --repin-tickets` mints new ones.
