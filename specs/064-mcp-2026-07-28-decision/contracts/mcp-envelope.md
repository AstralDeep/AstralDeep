# Contract: internal MCP envelope

## Additive fields

`MCPRequest` adds these top-level transport fields, never fields inside `params.arguments`:

- `protocol_version: str | None`
- `caller_capabilities: dict[str, object] | None`
- `caller_info: dict[str, object] | None`

Modern producers set `protocol_version` to `2026-07-28`, `caller_capabilities` to at least `{}`, and `caller_info` to their name/version identity. A modern consumer refuses a declared unsupported version or a modern request missing a required field before invoking a tool. A legacy request with none of the three fields remains acceptable only on the internal compatibility path during rollout.

`MCPResponse` adds:

- `result_type: str`, default `complete`
- `responder_info: dict[str, object] | None`

A response is either successful (`error is None`, `result_type` describes the result, and components may be present) or a protocol failure (`error` present and no renderable components). Tool execution failures remain completed tool results, not protocol failures.

## Unknown-key tolerance

Every decoder selects only declared dataclass fields before construction. Unknown additive keys are discarded. Missing required structural fields, wrong container types, and malformed JSON remain errors and must complete the associated pending future promptly; they must never be swallowed into the 30-second timeout.

`AgentCard.from_dict` applies the same forward-compatible card-key filtering. `AgentCard.to_dict` derives skill fields from `AgentSkill` serialization so future fields round-trip without another hand-written allowlist.

## Five dispatch implementations

1. **Bundled per-agent servers** (`backend/agents/*/mcp_server.py`): tolerate additive request keys, validate modern metadata, and emit the discriminator and responder identity. The ten near-copies are one implementation family.
2. **Draft/attachment-parser code generation** (`backend/orchestrator/agent_generator.py`): generated servers import the shared dataclasses and use the same filtered decoder and metadata fields.
3. **Generated BYO bundle runner** (`backend/orchestrator/agent_generator.py` bundle header and body): header and body together are one implementation; its stdio admission parser filters unknown keys and its responses carry the new fields.
4. **Windows desktop agent** (`windows-client/win_agent/agent.py`): filters request fields and includes discriminator/identity on replies.
5. **A2A executor bridge** (`backend/shared/a2a_executor.py` with `a2a_bridge.py` as carrier): parses and emits the expanded envelope without placing metadata in tool arguments.

The shared `base_agent.py`, `local_transport.py`, and `a2a_bridge.py` carriers preserve all known fields. The orchestrator's synthetic failures also emit a discriminator and identity.

## Rollout behavior

- New reader + old writer: absent additive fields are treated as legacy internal traffic; ordinary calls continue.
- Old reader + new writer: delivered/generated peers that splat keys are revalidated before use; in-tree readers are upgraded together. No silent timeout is accepted.
- New reader + new writer: required modern metadata is enforced and unsupported versions produce `-32022` with `supported: ["2026-07-28"]`.
- Fields outside the personal-agent fence allowlist remain fail-closed. The allowlist must include every field the orchestrator itself emits.

`result_type` participates in semantic response validation but not the legacy response digest during the compatibility window, preserving already-delivered bundle digest verification. The digest contract may be versioned separately after all delivered bundles are revalidated.
