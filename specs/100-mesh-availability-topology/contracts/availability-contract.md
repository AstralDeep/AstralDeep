## 1. Decision

**Selected topology: T1 — single durable authority per deployment with bounded in-place recovery.**

A personal mesh is a federation of independent Astral deployments joined through the governed mesh/bridge surfaces. Availability is decided **per deployment**; no shared durable authority, cross-deployment transaction, or mesh-wide scheduler is introduced. Within one deployment:

1. Exactly **one active orchestrator process group** serves admission, dispatch, and clients.
2. Exactly **one durable authority**: the embedded AstralPlane runtime over its PostgreSQL database, bound once at boot by [`backend/orchestrator/plane_composition.py`](../../../backend/orchestrator/plane_composition.py) and failing closed on any contract drift.
3. Exactly **one configured blob root** for attachment/artifact content, host-bound by design.
4. Loss of any node **fails closed and recovers in place**: interrupted work is resumed or surfaced honestly through lease expiry and re-claim; delivery is at-least-once with fenced redelivery; uncertain external effects are never auto-resolved and require the owner's digest-bound reconcile decision.
5. Disaster recovery beyond a live node is **operator-managed backup/restore** with explicit attestation; the restore path retires sessions and verifies the restored catalog before admission reopens.

**Why T1 fits the governing boundaries.** AstralPlane's constitution fixes Plane as an embedded library whose only database is PostgreSQL — "MUST NOT add a service port or a second database". AstralDeep's constitution (Principle IX) forbids borrowing connections or a second migration framework. The mesh's host-bound stores (blob root, personal-agent artifacts, the orchestrator's private ephemeral archive and evidence archive) make a second active orchestrator unsafe today, and a distributed database is explicitly left as a design question by the issue. T1 is the strongest availability posture those boundaries permit *without new mechanics*, and it is honest about what it does not promise.

### Compared options (all within Plane's embedded-PostgreSQL boundary)

| Option | Shape | Consistency | Recovery available today | Verdict |
| --- | --- | --- | --- | --- |
| **T1 — single durable authority, recover in place** (selected) | One orchestrator group; embedded PostgreSQL sole authority; one blob root | Single-writer; owner-scoped fenced writes; at-least-once delivery with idempotent absorption | Lease expiry + re-claim; fenced outbox redelivery; owner reconcile of uncertain effects; operator restore | **Selected.** Matches the existing verified mechanics (C-03, C-04, C-05, C-07); no new backend; honest degraded states. |
| **T2 — orchestrator replica pair sharing one PostgreSQL** | Two orchestrator processes, one database; DB-authoritative work-claim handover | Still single-writer at the database; split-brain bounded by execution fences | Work claims hand over via lease expiry; *but* blob root, artifacts, and archives are host-bound, so content-serving replicas diverge | **Not selected; bounded future option.** The durable-work half is mechanically available (fencing is in the database), but supporting replicas first requires shared/replicated blob and archive mechanics — a Plane design question. Imposing it now would trade silent content divergence for perceived availability. |
| **T3 — distributed/consensus database (quorum SQL or similar)** | Multiple durable nodes; consensus replication | Eventual or quorum consistency; new failure modes (partial partitions, membership changes) | Automatic failover | **Rejected for this decision; remains an open design question.** Requires a second database or replacing the embedded boundary — barred by Plane's constitution and explicitly not to be imposed by this issue. Preconditions for ever selecting it are recorded in [§6](#6-unsupported-states-and-deferred-design-questions). |
| **T4 — operator-managed warm standby via backup/restore** | Same T1 runtime; second host restored from backups on demand | Restored copy is consistent to the backup point; sessions retired post-restore | Restore + attestation + catalog verification + session retirement | **Supported as the disaster-recovery path (F-7).** RPO = backup cadence — the only non-zero RPO in this decision. |

## 3. Failure matrix

Every failure class states its detection, consistency behavior, RPO, RTO disposition, honest degraded state, and recovery action. RTO dispositions are **bounded by named mechanisms** (boot gates, lease defaults, poll cadence); this decision deliberately promises no wall-clock numbers — CI gates must stay deterministic (Constitution XI), and a personal deployment's real numbers are a qualification-time measurement, not a specification claim. RPO is 0 for anything committed to the durable authority; the only non-zero RPO in the topology is the operator's backup cadence (F-3/F-4/F-7).

| Id | Failure class | Detection | Consistency | RPO | RTO disposition | Honest degraded state | Recovery action |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **F-1** | Orchestrator process/host loss | Clients lose transport; process manager observes exit; no in-process state survives | Committed state is intact (single durable authority); in-flight work holds only its durable lease | 0 for committed durable state | Restart + boot: composition pin verified, migrations verified, health gate must pass before readiness; expired leases make work re-claimable | `admission_unavailable` while down; after restart, uncertain attempts remain honestly unresolved | Process manager restarts; `expire_execution_leases` + re-claim resume interruptible work; uncertain effects go to owner reconcile (C-04, C-05) |
| **F-2** | Executor loss (remote machine/agent running a tracked job) | Poller observes missing/stale job state; orphan/fail thresholds (`_orphan`, `_touch_fail`) | Job records durable; wake events delivered through durable waiters/outbox | 0 | Bounded by poll cadence + fail threshold (design constants, no wall-clock promise) | `effect_unconfirmed`: owner sees `orphaned`/`unconfirmed`, never silent `completed` | Owner decides via digest-bound reconcile (`confirmed_applied`/`confirmed_not_applied`); rescheduling without that decision is forbidden (C-06, C-05) |
| **F-3** | PostgreSQL (durable authority) loss or corruption | Pool/connect failures; boot health gate refuses readiness; every write path fails | No partial availability: the deployment is down, not inconsistent — there is no fallback store and no degraded read mode | Backup cadence (operator-managed) — the only non-zero RPO | Operator-bounded: restore, attestation, boot | `durable_unavailable`: full stop; admission closed; nothing claims success | Restore named backup; verify schema revision + migration digest; run post-restore session retirement; boot (C-08, C-09, F-7) |
| **F-4** | Blob root loss (attachments/artifact content) | Store read/close errors; materialization failures surface as unavailable, not as substitutes | Durable metadata (records, digests) stays authoritative and consistent; content unavailability never rewrites records | Blob-root backup cadence (operator-managed) | Restore blob root; affected surfaces return when content returns | `blob_unavailable` on attachment/artifact surfaces; honest per-surface, no silent regeneration or substitution | Operator restores the blob root from backup; materializations fail closed until then (C-10) |
| **F-5** | Mesh member/device loss (stops publishing presence) | Presence TTL expiry (default 300 s; clamped 30–3600 s); resolver reasons `stale_observation`/`unpublished` | Enrollment/membership durable; presence is ephemeral advertisement, not durable truth | n/a — presence is TTL-bounded advertisement | A member stops being advertised live at most one TTL after its last observation | Honest `offline`/`unavailable` presence with a stated reason in owner topology reads; no false `online` | Member republishes a possession-bound presence observation; membership itself needs no recovery (C-11) |
| **F-6** | Delivery failure (outbox worker dies mid-lease) | Lease expiry; `reclaim_expired` returns entries to claimable state | At-least-once delivery; fence inputs bind `(entry_id, worker_id, expected_version)` so a stale worker cannot ack or retry; consumers absorb duplicates via submission receipts and event-key waits | 0 until explicit dead-letter; dead-letter is a visible terminal, never a silent drop | Next claim cycle redelivers | `delivery_delayed` until reclaimed; duplicate delivery possible by design and MUST be absorbed idempotently | Redelivery on reclaim; `retry`/`dead_letter` bound the loop explicitly (C-07) |
| **F-7** | Disaster restore (F-3/F-4 beyond live recovery) | Operator-initiated; never automatic | Restored catalog must match the current schema revision and migration digest exactly, or admission stays closed | Backup cadence | Operator-bounded restore time + boot verification | Post-restore: all sessions retired; every client re-authenticates — stated, not hidden | `retire_restored_sessions` refuses non-current revision/digest and wrong database/schema before any connection; boot re-verifies the full catalog (C-09) |

**Consistency model.** One durable authority per deployment; every repository write carries its owner predicate and version/idempotency fence in the same statement (Plane Constitution III). Delivery to parties outside the transaction is **at-least-once with fenced redelivery**; idempotent absorption is a consumer obligation met today by submission receipts, idempotent operation keys, and event-key waits. Effects that cross the deployment boundary (remote executor work, external side effects) are **not** inferred complete from rescheduling: uncertainty is a first-class durable state resolved only by the owner's digest-bound decision. Across deployments, the mesh offers membership and attested transport — never shared transactions; each deployment remains its own availability domain.

Each promise is **specified**: its executable case ships and passes today; the qualification evidence classes named alongside are required *before any deployment/release/availability claim*, and none of that evidence exists yet. Nothing here asserts deployment or release.

| Id | Promise | Required evidence |

| **P-1** | Committed durable work survives orchestrator or executor loss and is either resumed (lease re-claim) or surfaced honestly (retryable/orphaned/unconfirmed) — never silently dropped. | Executable now: **C-03**, **C-04**, **C-06**. ## 5. Work and client recovery summary

- **Work recovery promises**: queued and leased operations survive orchestrator restart (durable admission + leases); RUNNING work whose lease expires becomes re-claimable and its stale executor is fenced out; tracked remote jobs resolve to honest outcomes (`completed`/`failed`/`cancelled`/`orphaned`/`unconfirmed`) with uncertain outcomes gated on owner reconcile; scheduled/maintenance classes follow the same durable admission path. What is *not* promised: automatic migration of work to another deployment, automatic retry of unproven effects, or completion guarantees for effects whose executor died without evidence.
- **Client recovery promises**: durable waits (owner event waits, tracked-job waits) survive restarts and replay safely via submission receipts; membership, enrollment, and conversation/session records are durable in Plane; after a disaster restore every client re-authenticates (sessions retired by the attested restore path); presence a client sees is TTL-bounded and honest. What is *not* promised: transparent session continuation across orchestrator hosts (T2 territory), zero-reconnect client experience across a PostgreSQL loss, or cross-deployment single sign-on beyond the existing Keycloak/RFC 8693 boundaries — which are preserved untouched by this decision.

## 6. Unsupported states and deferred design questions

Explicitly unsupported by the selected topology; the conformance suite fails closed if the repository starts implying any of them:

1. **Multiple simultaneously active orchestrators** against one embedded PostgreSQL with today's host-bound blob root, personal-agent artifacts, and evidence/private archives. (T2 precondition: shared/replicated blob and archive mechanics in Plane — a design question, not imposed here.)
2. **Automatic failover to a standby durable authority**, and any second database, second migration framework, or borrowed-connection path beside the composed Plane runtime.
3. **A distributed/consensus database** (T3). Deferred as a design question with preconditions: a Plane constitutional amendment permitting a second durable backend; a consistency/failure-mode analysis; and qualification evidence for mesh-scale failover. Until then it MUST NOT be imposed by any child of this tracker.
4. **Zero-RPO disaster recovery**. Without operator-managed continuous archiving, the honest RPO for disaster classes is the backup cadence; claiming otherwise is forbidden.
5. **Cross-deployment transactions, mesh-wide work migration, or a mesh-wide scheduler.** Each deployment remains its own availability domain; the mesh joins deployments, it does not merge them.
6. **Rescheduling uncertain effects to success without proof**, and any "availability" number presented as a specification guarantee rather than a qualification-time measurement.

## 7. Conformance cases

Machine-readable expectations: [`availability-cases.json`](availability-cases.json). Binding test module: [`backend/tests/test_mesh_availability_topology.py`](../../../backend/tests/test_mesh_availability_topology.py). Every case is deterministic and fails closed on drift.

- **C-01** — Case registry integrity: unique ids, declared kinds, every id referenced here and bound to a real test; the registry's `status` matches this document's status sentence exactly.
- **C-02** — Single durable authority boundary: no `backend/shared/database.py`; exactly one `data_plane` pin in `config/astral-composition.json`; no distributed-DB driver in `backend/requirements.txt`; this contract records the distributed database as deferred, not selected.
- **C-03** — Lease/fence surface: `WorkAdmissionCoordinator` default `slot_lease` is 30 s and the lease/fence methods exist; Plane raises `StaleWorkExecutionFenceError`.
- **C-04** — Stale fences are invalidated: a stale execution fence cannot terminalize (raises `StaleExecutionFenceError`) and `reselect_execution` issues a new execution generation.
- **C-05** — Uncertain effects need an owner decision: `WorkReconcileRequest` accepts only `confirmed_applied`/`confirmed_not_applied` with a 64-hex `prior_result_digest`; anything else is a validation failure.
- **C-06** — Executor loss is honest: `confirmed=False` outcomes are distinct (`unconfirmed`/`orphaned`), never silently `completed`; the tracked-job wake path and orphan/fail handling exist.
- **C-07** — Outbox redelivery is fenced: `claim`/`ack`/`retry`/`dead_letter`/`reclaim_expired` exist, claim is lease-based, and fence inputs bind entry, worker identity, and expected version.
- **C-08** — PostgreSQL/contract loss fails closed: a tampered composition expectation is reported incompatible with named reasons and `compose_plane_catalog` raises.
- **C-09** — Restore is operator-attested: `retire_restored_sessions` requires keyword-only attestation of database, schema, revision, and digest, and refuses incompatible attestation before any connection attempt.
- **C-10** — Blob root resolution fails closed: missing/relative/empty `ATTACHMENT_UPLOAD_ROOT` is refused; the default root is the bounded backend-local default.
- **C-11** — Presence is honest: TTL default 300 s clamped to 30–3600 s (including non-numeric env), with `offline`/`unavailable` states and stated reasons.
- **C-12** — Recovery promises carry evidence: every promise id appears here, has non-empty required evidence, and is marked `specified`.
- **C-13** — Failure-matrix completeness: the matrix row set matches the declared failure classes exactly, every row carries all required fields, and each id is referenced in this document.
